# 相关工作

这里只写 2026-11-18 实际打开过的来源。每一节的顺序是：一段结论、结构类型、它优化什么、为什么进或不进 v1。v1 的选择理由在最后一节收束，实验设计在 [03-benchmark-design.md](03-benchmark-design.md)。

本仓库没有复现任何一篇论文的实验，也不把它们的分数当成自己的结果。

## 1. Cairn（oritera/Cairn）

Cairn 和 nvwabase 是近亲：共享板上的事实与意图，外加随时写入的 hint。nvwabase 的 README 明确写了参考 Cairn 来给 AI 记历史。Cairn README 把渗透测试说成“起点和目标已知、路径未知”的状态空间搜索，并称同一形状也覆盖漏洞研究、数学证明和 CTF。它用黑板架构，三个原语是 Fact（已确认的客观发现）、Intent（尚未执行的探索方向）、Hint（人的判断，代理下次读取时吸收）。工人跑 OODA，只通过黑板协调（README 使用 Stigmergy 一词）：没有直接通信，没有固定角色。任务在运行时从当前图长出来，类型是 Bootstrap、Reason、Explore。系统分成维护图一致性的 Server、调度并写协议的 Dispatcher，以及工人容器；也可以不使用 Docker 的 local 模式。支持的工人后端写的是 Claude Code、Codex、Pi。许可证在 GitHub API 上是 AGPL-3.0；README 另要求商业使用另行联系。

README 报告第二届腾讯云黑客松 AI 渗透挑战：610 支队伍、1345 名参与者、54/54 题、排名第 3，并写“赛前没有测过、零 MCP、零 RAG、零预定义角色”。这是项目自述，不是知识库结构的消融实验。

- **结构类型：** 事实—意图—提示的黑板图。事实是落脚点，意图是走向未知的一步，图从 origin 长到 goal。
- **优化目标：** 在未知路径上持续搜索，并用一块板代替代理之间的直接对话。
- **v1：** 不作为独立的一臂。它和图臂在原语上重叠，同时绑着服务器、调度器和容器。若把整个 Cairn 对上一个向量库，变的就不是结构。以后只有把黑板抽成和 v1 相同的读写接口、去掉调度器，才值得单独立臂。AGPL 也要在那时单独看怎么引用代码。

## 2. GraphRAG（微软）

Edge 等人的论文 *From Local to Global: A Graph RAG Approach to Query-Focused Summarization*（arXiv:2404.16130）要解决的是：普通 RAG 不擅长针对整库的全局问题（例如“这批材料的主题是什么”），而传统的查询聚焦摘要又扩不到 RAG 那种语料规模。做法是让 LLM 从源文档抽出实体知识图（节点是实体，边是关系），再用社区检测把图分成层级社区，自底向上为社区写摘要；回答全局问题时，对社区摘要做 map-reduce。论文图 1 的说明把社区检测的例子写成 Leiden。论文摘要称，在约一百万 token 量级的全局理解问题上，相对常规 RAG，答案的 comprehensiveness 和 diversity 有明显提升。本仓库没有复现，也不把这句话外推到“代理边做边写”的工作记忆。

开源实现是 [microsoft/graphrag](https://github.com/microsoft/graphrag)。2026-11-18 打开的 README 把项目标成维护模式：自 2024 年 7 月首次发布后不再接受新功能 PR，索引可能很贵，代码是演示而不是受支持产品。

- **结构类型：** 从静态语料抽出的实体图，加上层级社区摘要。边表示抽取出的关系，不表示“下一步要做的工作”。
- **优化目标：** 对一份已经写好的私有文本做全局问答，并用预计算摘要换查询时的覆盖面。
- **v1：** 不进入。v1 的记忆是会话中不断追加的工作记录，查询次数远少于写入次数，而且要支持交接和并发写。GraphRAG 的索引发生在查询之前，社区摘要是另一套 LLM 开销。它可以作为以后的“把已有笔记再索引成实体图”臂，但要单独计索引 token，不能和边写边查的三臂放在同一个预算里假装公平。

## 3. 向量 RAG / 分块记忆

Lewis 等人的 *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*（arXiv:2005.11401，页面标明 v4，2021-04-12）把非参数记忆做成维基百科的稠密向量索引，用预训练的神经检索器取出文档，再交给 seq2seq 生成。文中比较了两种用法：整段生成条件于同一批段落，或每个 token 可以条件于不同段落。论文的任务是开放域问答、生成和事实核验，检索库是事先建好的，不是代理在工作中追加的笔记。

后来的工程实践把“切块、嵌入、按相似度取回”用到了代理记忆上。Letta 2025-07-07 的文章把向量库写成归档记忆的一种存储，并写了一句边界：检索是记忆的工具，检索本身不等于记忆。MemGPT 论文的文档问答设置里，归档存储用的是余弦相似度（文中为 OpenAI `text-embedding-ada-002` 与 pgvector）。这些说明向量分块已经被当作外部记忆的一种实现，同时论文原式和“会话中可写的笔记库”不是同一个系统。

- **结构类型：** 无类型文本块的向量索引。关系若存在，只存在于文本里，或存在于“和这条块一起被取回”。
- **优化目标：** 在大段文本里按相似度找出可能相关的片段，并把它们放进有限的上下文。
- **v1：** 进入，作为基线。进入的是**适配后的工作记忆**：代理可以把观察写成块，按查询取回最多 k 块，每轮注入有相同的 token 上限。不进入的是 Lewis 等人的端到端微调、维基百科索引，以及 RAG-Sequence / RAG-Token 的概率形式。嵌入模型尚未选定；选定之前，这一臂的“结构”仍然和“用哪个检索器”缠在一起。这一点写进设计文档的未决问题。

## 4. 扁平笔记 / markdown 记忆

Claude Code 的文档 *How Claude remembers your project*（2026-11-18 打开，<https://code.claude.com/docs/en/memory>）描述了两种一起加载的机制。`CLAUDE.md` 是人写的说明，会话开始时读取；文档写明，启动时加载的每个 `CLAUDE.md` 在不超过 4 MiB 时整文件进入上下文，超过则整文件跳过。自动记忆是另一套：每个仓库一个目录，`MEMORY.md` 是索引，详细内容在按主题拆开的文件里；每次会话只加载 `MEMORY.md` 的前 200 行或前 25 KB（以先到者为准），主题文件按需再读。文档把二者都称为上下文，而不是强制配置。

这给出一个已经在产品里使用的极端：不建图、不建向量，把一份 markdown 放进上下文，用长度上限控制膨胀。自动记忆的“索引 + 按需主题文件”已经比单文件多了一层，更接近下一节的分层，而不是纯扁平。

- **结构类型：** 一份顺序追加的 markdown。位置就是顺序，没有类型化的边。
- **优化目标：** 实现简单，人可以直接改，会话之间靠“下次把文件再读进来”延续。
- **v1：** 进入，作为最弱结构基线。基准里的这一臂是自写的适配器：单个笔记文件，追加观察，每轮注入不超过统一预算；超预算时保留文件尾部（最近写入），并在日志里记被截掉的字符数。它借鉴 Claude Code“整文件注入、另有硬上限”的做法，但不调用 Claude Code，也不把自动记忆的主题文件算进这一臂。主题文件更适合以后和 MemGPT 式分层放在一起比较。

## 5. 分层摘要记忆（MemGPT / Letta）

Packer 等人的 *MemGPT: Towards LLMs as Operating Systems*（arXiv:2310.08560，页面标明 v2，2024-02-12）把上下文窗口当成主存，把窗口外的存储当成磁盘。主上下文包含系统说明、working context 和一条 FIFO 队列。窗口外是 archival storage（任意长度文本，可检索）和 recall storage（对话历史）。模型通过函数调用自己决定把什么换入、什么换出。队列超过警戒线时，系统提醒模型先把重要内容写出去；刷新时丢掉一部分消息，并用旧摘要加上被丢掉的消息生成新的递归摘要。论文在两类任务上评估：超过窗口的文档分析，以及跨会话聊天。文档问答实验里，MemGPT 可以多次查询归档库并翻页，固定上下文基线则一次拿到检索器给出的 top-k。

Letta 的说明（2024 年的 [MemGPT Is Now Part of Letta](https://www.letta.com/blog/memgpt-and-letta/)）把 “MemGPT” 收成论文里的设计模式，把框架命名为 Letta。2025-07-07 的 [Agent Memory](https://www.letta.com/blog/agent-memory) 把组件写成：最近消息缓冲、钉在上下文里的 core memory blocks（有标签、说明、值和字符上限，代理可改写）、可搜索的完整对话（recall）、以及归档记忆。同文在概念上写归档层可以采用向量库或图数据库，并描述了睡眠期代理：在对话之外整理记忆。本次打开的归档记忆 API 文档（<https://docs.letta.com/v1-sdk/memory/archival-memory/>）把这层具体写成向量库：片段不能钉在窗口里，代理用 `archival_memory_insert` / `archival_memory_search` 按语义存取，文档并写代理不易自行修改或删除这些片段。概念文章里的“图数据库”和当前 API 页上的“向量库”不是同一句话，本仓库不把它们合成一种实现。

- **结构类型：** 至少两层。一层始终在上下文里（工作上下文或 memory block，外加递归摘要），一层在外部，靠函数调用分页取回。2025-07-07 的概念文章把归档层的存储写成向量或图两种可能；本次打开的 API 文档把归档层实现写成向量库。分层方式和底层索引仍是两个旋钮，但不能从概念文章直接读出当前 API 已经提供图归档。
- **优化目标：** 在固定窗口里维持可用的工作集，并把溢出的历史留在可查的外部存储里。
- **v1：** 不进入运行臂。它优化的是记忆**策略**（何时摘要、何时分页、谁来改写钉住的块），不只是存储形状。若直接采用 Letta 运行时，模型、工具循环和结构会一起变。v1 的三臂已经用统一的注入预算粗略模仿“主上下文有限”。完整的自管理分页留到接口稳定之后：那时可以加第四臂“钉住的摘要块 + 外部可搜索存储”，并规定摘要由同一个模型在同一预算下生成。

## 6. 代码属性图（CPG / Joern）

Yamaguchi 等人的 *Modeling and Discovering Vulnerabilities with Code Property Graphs*（IEEE S&P 2014，本次打开的是会议站点上的 PDF）定义的 code property graph 把抽象语法树、控制流图和程序依赖图放进同一张属性图，用图遍历表达漏洞模式。论文摘要写，该方法在 Linux 内核源码中找出 18 个先前未知的漏洞。那是静态分析的结果，不是 LLM 知识库实验。

Joern 文档（<https://docs.joern.io/code-property-graph/>，2026-11-18）把现行 CPG 描述成带类型节点、带标签的有向边和键值属性的属性图，用来在多种语言的代码里挖掘编程模式。文档回顾 2014 年的核心想法：语法、控制和过程内数据流进同一结构，用遍历语言跨这些视图查询。后续工作把过程间分析和其他表示加了进去，并换成项目自己的图库。节点可以表示方法、变量、控制结构，也可以表示更高层的端点或 finding。

- **结构类型：** 程序的中间表示。节点是程序构造，边是语法包含、控制流或数据依赖，不是代理的工作项。
- **优化目标：** 让分析者（或规则）在一张图上同时看语法、控制和数据流，从而定位代码模式。
- **v1：** 不作为被测的知识库结构。它回答的是“程序长什么样”，不是“代理确认了什么、下一步做什么”。若某一臂独享 Joern 而其他臂没有，比的是静态分析工具。以后它可以作为**所有臂共用的只读证据工具**（例如按函数取出调用者），那时它在自变量之外。在那之前，v0.1 连这个工具也不提供，避免和知识库结构缠在一起。

## 7. v1 收束

v1 只保留三种能接到同一组操作上的结构（操作定义见设计文档）：

| 臂 | 来源 | 放进 v1 的理由 |
|---|---|---|
| 事实—意图图 | nvwabase `lib/fg.py` 的无类型三层图 | 本仓库的起点；边表达依赖与工作项，详细层默认不进上下文 |
| 向量分块 | Lewis 等人的非参数记忆，改成会话中可写 | 最常见的“按相似度取回”基线 |
| 扁平 markdown | Claude Code 文档中的整文件注入加硬上限 | 最弱基线；实现差异最小 |

明确不放进 v1 运行的：Cairn 全系统、GraphRAG 索引、MemGPT/Letta 运行时、Joern、sapper 的类型化事实和离线 `kb/`。它们都有理由以后再加，但每一项都会多改变一个不只是“结构”的变量。
