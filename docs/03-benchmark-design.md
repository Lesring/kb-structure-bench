# 基准设计 v1

**这是设计，不是结果。** 下面没有测量值。凡是写成具体数量的地方，都是待定参数或建议的起点，开工前要写进配置并在日志里冻结。本设计不包含利用载荷、PoC 或攻击步骤。任务只要求代理判断缺陷是否存在、属于哪一类、位于何处、依据是哪段代码，并在交接后仍能答对。

## 1. 研究问题

在模型、工具、任务和每轮证据预算相同的前提下，哪一种知识库**结构**让长周期代理工作更有效，也更省上下文？第一块下游任务是程序分析里的漏洞发现：代理要在一次会话中形成发现，并在会话结束后把发现交给另一个看不到源码、也看不到原对话的代理。

“有效”指交接后的判断、类别、位置和证据引用是否与标签及源码一致。“省”指达到该判断所注入和生成的 token、墙钟时间，以及每次取回的上下文大小。本设计不假设图结构会赢。sapper-v2 的比赛叙述不能用来回答这个问题，原因见 [01-nvwabase.md](01-nvwabase.md)。

## 2. v1 要比较的结构

三臂，对应 [02-related-work.md](02-related-work.md) 的收束：

1. **事实—意图图。** 行为对齐 nvwabase `lib/fg.py` 的无类型模型：事实节点含 `title` / `description` / `doc`，意图是带 `from` / `to` 的工作项，默认注入只有标题和摘要，`doc` 按 id 另读，搜索是 title 加权的 token 重叠加 `difflib` 后备。实现可以是直接调用 `fgc`，或按该文件的字段写一个适配器。不使用 sapper 的 `kind` / `data`，不使用 `nvwa` 派发，不使用仓库自带的 `dispatch` 模板。
2. **向量分块。** 每次 `write` 追加一个文本块并更新嵌入。`search` 按余弦相似度返回最多 k 块。没有边。若代理要表达“A 依赖 B”，只能把这句话写进块文本。嵌入模型是未定参数，三臂里只有这一臂使用它，因此日志必须记录模型名和维度。
3. **扁平笔记。** 单个 markdown 文件，`write` 追加一节。每轮注入预算用尽时保留文件尾部。`search` 是大小写不敏感的子串扫描，命中节按预算截断返回；没有向量，也没有边。

三臂都不预载漏洞百科、CWE 全文或项目自带的渗透笔记。空库开始。

## 3. 共用的代理接口

结构是自变量。代理只看到下面这组工具，三臂的工具名、参数和错误文本相同。适配器在内部映射到各臂。

| 工具 | 参数 | 各臂怎么做 |
|---|---|---|
| `kb_write` | `title`，`body`，可选 `depends_on`（id 列表） | 图：`title`→title，`body` 的首行→description，全文→doc；若给了 `depends_on`，另建一条意图，`from` 为这些 id，`to` 为新事实。向量：一块文本，`depends_on` 仅作为正文里的一行。笔记：追加一节，同样把依赖写成正文 |
| `kb_search` | `query`，`limit` | 图：`recall` 的重叠打分，命中后不自动带 doc。向量：top-k 余弦。笔记：子串命中 |
| `kb_read` | `id` | 图：返回该节点的 doc（没有 doc 就返回 description）。向量和笔记：返回该块或该节的全文 |
| `kb_list` | `limit` | 返回 id、title、一行摘要。图臂不要把 doc 放进列表 |

每轮自动注入的内容也相同：`kb_list` 的结果，截断到**同一个**字符或 token 预算 `B_inject`。预算的数值未定。图臂原有的 6000 字符和“最近 8 条”不自动沿用，否则图臂的策略就混进了结构。

`depends_on` 让图臂能存一条真边，另外两臂只能存一句话。这是结构差异本身，不是额外功能。代理提示词三臂共用，不解释哪种后端更强，也不提示“请多建边”。

代理在任务阶段还可以使用的程序工具只有：列出给定目录、读取给定文件、在给定文件内做字面搜索。没有壳命令、没有包管理器、没有动态运行、没有 Joern、没有网络。文件范围限制在该题的已脱敏源码目录。

写入会话的模型、解码参数、最大步数 `N_steps`、单次工具输出上限，三臂相同。交接代理是一次新的上下文，模型与参数相同，看不到写入会话的消息。

## 4. 下游任务

### 4.1 问什么

对每一题，标签（代理不可见）至少包含：是否存在被数据集标出的缺陷、缺陷类别（CWE 或数据集自己的类别名）、位置（文件与函数；有行号则用行号）。代理最终要交一张结构化答案，字段只有：

- `vulnerable`：`yes` / `no` / `unknown`
- `category`：类别字符串或 `unknown`
- `location`：文件、函数、可选行号，或 `unknown`
- `evidence_ids`：知识库记录 id 列表
- `notes`：不超过固定字数的说明，禁止步骤化的利用过程；评分程序若在该字段里匹配到载荷样式，整题记为无效而不是加分（样式表本身还没写，v0.1 先做人工抽查）

写入阶段的指令是：阅读给定源码，把确认了的观察写入知识库，最后不必输出答案。交接阶段的指令是：只根据知识库回答上述字段，并引用记录 id。交接代理**不能**再读源码。这样测到的是知识库有没有保住发现，而不是第二个模型会不会自己重做分析。

这个设计会让“写得太少”的结构集体失败。那仍然是关于结构（以及共用写提示）的信息。若 v0.1 三臂都接近地板，先检查提示和预算，再考虑增加一臂对照：交接代理同时看见源码和知识库。那一臂测的是知识库会不会帮倒忙，不放进 v0.1。

### 4.2 数据集

**v0.1 使用 Juliet C/C++ 1.3**（NIST SARD 测试套件 112，<https://samate.nist.gov/SARD/test-suites/112>）。页面写明：NSA Center for Assured Software，C/C++，64099 个测试用例，118 个 CWE，2017-10-01 提交；1.3 相对 1.2 增加了自增/自减用例并修正了一批系统性问题。许可页面写明在美国不受版权保护、属于公有领域，并在 NIST 可主张外国权利的范围内以 CC0 1.0 提供。本仓库尚未下载压缩包，也尚未逐文件检查注释里是否重复了 CWE 说明。

Juliet 适合做第一刀，因为它有显式标签、用例短、许可清楚。它不适合被说成真实漏洞分布：用例是合成的，同一缺陷配有大量控制流变体。v0.1 的目的只是看结构在“标签已知、文本不长、但名字会泄题”的条件下能否保住发现。

**必须先做的脱敏，否则标签会直接躺在文件名和函数名里。** 已知风险：SARD 页面上的用例说明包含 CWE 编号、BadSource / GoodSource、BadSink 等字样；Juliet 的常规命名也把 CWE 和 good/bad 编进路径与函数名。v0.1 的预处理是：

- 金标签写入运行目录之外的文件，文件名用随机 id。
- 交给代理的副本删除原路径，函数名和文件名换成 `fn_1`、`file_1.c` 这类无信息名字，并删掉含 `CWE`、`good`、`bad`、`sink`、`source` 的注释行。替换表只留在评分侧。
- 预处理之后人工抽查至少 10 个文件，确认标签词没有留在源码字符串里。抽查清单还没做。

**建议的 v0.1 样本，仍是待定参数：** 8 个 CWE，每个 CWE 取 1 个带缺陷用例和 1 个对应的无缺陷变体，共 16 题。CWE 名单在抽查命名规律之后再定，不在本文假装已经选定。每个题 × 每臂重复 3 次，因为模型输出会抖动；3 不是功效分析的结果，只是第一轮想看见方差。合计 16 × 3 × 3 = 144 次写入会话，外加同样次数的交接。这个规模是为了能看完轨迹，不是为了显著性。

## 5. 指标

全部是定义。没有基线数字，也没有“期望提升”。

### 5.1 有效性

在交接代理的结构化答案上计算，金标签只在评分时打开。

- **判断准确率。** `vulnerable` 与标签一致的题数 / 题数。`unknown` 算错。另报未知率，避免模型用未知换准确率时看不见。
- **类别准确率。** 在标签确有缺陷的题上，`category` 与 CWE 编号一致的比例。无缺陷题不计入类别分母。字符串必须完全等于标签，不做同义词合并，除非事先写好一张映射并冻结。
- **位置命中。** 标签中的文件（脱敏后的 id）和函数名出现在 `location` 里。行号若标签没有，就不评行号。
- **完整性。** 一题若同时有缺陷判断、类别和位置，三项都对才算完整。报告完整题的比例，不与准确率混成一个分数。
- **证据忠实度。** 对每个 `evidence_ids`：该 id 必须存在于本题知识库；记录正文必须包含一段也出现在**交给写入代理的源码**里的连续片段（建议长度 ≥ 20 个非空白字符，长度未冻结）。引用了不存在的 id、或片段不在源码里，记一次不忠实。分母是提交的 evidence id 数。这衡量的是“知识库里的话是否真从源码来”，不是“结论是否正确”。正确但没有忠实引用，忠实度为 0，准确率照常另计。

### 5.2 效率

- **Token。** 写入会话与交接会话分开记输入 token 和输出 token。计数器以所选模型 API 返回的 usage 为准；若接口不返回，则用该模型公布的分词器本地重算，并在日志里标明来源。两种来源不能混在一个平均数里。
- **时延。** 墙钟时间，从进程开始到答案落盘，含工具调用。同时记知识库操作自身的时间（不含模型）。
- **检索与上下文大小。** 每次 `kb_search` / `kb_read` / 自动注入的返回字符数，以及这些字符折成的 token 数。报告中位数和最大值，不只报告均值。

### 5.3 交接、并发和自相矛盾

- **交接落差。** v0.1 的主读数就是交接后的准确率。写入代理不交最终答案，所以没有“交接前准确率”可减。若以后让写入代理也交一份答案，落差定义为交接准确率减去写入准确率，两项用同一评分程序。
- **并发写。** v0.1 不跑。定义留在这里：两个写入代理在无共享对话的情况下，对同一题追加知识库；评分看最终库是否同时含两边的记录、记录 id 是否冲突、文件是否可解析。图臂还要看 `fgc validate`（或等价检查）是否报结构错误。语义冲突不由文件锁保证，见下一行。
- **幻觉与矛盾率。** 幻觉用上面的证据忠实度覆盖“源码里不存在的引用”。矛盾另计：同一题的知识库里，若两条记录对同一函数给出相反的 `vulnerable` 判断（从记录正文里的固定句式提取，句式在提示词里规定，例如单独一行 `CLAIM vulnerable=yes|no`），计一对矛盾。分母是本题的记录对，不使用未选定的蕴含模型。提取失败的记录单独计数，不塞进矛盾率。

## 6. 协议

保持不变的量：

- 模型标识、温度、最大输出长度
- 第 3 节的工具集合与工具描述文本
- 写入提示词与交接提示词
- `B_inject`、`N_steps`、`kb_search` 的 `limit`
- 脱敏后的源码与随机题号
- 空的初始知识库
- 评分程序版本

一次运行的记录至少包括：题号、臂、重复编号、模型、全部工具参数和返回、知识库的最终快照、token 计数来源、开始与结束时间、交接答案。轨迹以 JSONL 存在本题目录，知识库快照用只追加的方式保存。金标签目录不在代理的工作目录内，也不写进轨迹的提示部分。

防止泄题的规则：

- 预处理在评分机上完成，代理工作目录里没有 CSV、没有 SARD 说明、没有原文件名。
- 提示词不出现 CWE 列表。类别字段允许代理填写它自己判断的编号；评分类别时只做字符串相等。
- 不把 Juliet 的官方说明页放进工具可读取的路径。
- 重复运行不共享知识库。向量索引按运行隔离。
- 若使用会保留服务端历史的托管模型，每题使用新的会话标识，并在日志里记录该标识。本设计没有验证任何一家托管服务是否真的隔离历史。

失败运行（进程崩溃、超步数、答案 JSON 无法解析）保留轨迹，准确率分母仍包含该题，分子记 0，并单列失败率。不重跑到成功再入样。

## 7. 效度威胁与范围外

- **结构与检索器缠在一起。** 图臂的搜索是 token 重叠，向量臂是嵌入，笔记臂是子串。v1 测的是“结构加它自然带的读取方式”。若要声称纯结构效应，需要另做一臂：同一种检索器、不同的组织方式。v1 不做这一臂，结论表述必须带上检索器。
- **合成数据。** Juliet 上的名次不能外推到 PrimeVul 或真实代码库。短文件对扁平笔记尤其有利，因为预算可能装得下全文。要在日志里报告每题源码 token 与 `B_inject` 的比值；比值接近 1 时，这题不能用来谈论“长上下文”。
- **脱敏可能删掉有用代码。** 按关键字删注释可能伤到字符串常量。抽查就是为了发现这件事。抽查通过之前不跑全样本。
- **交接代理看不到源码，任务偏难。** 见 4.1。地板效应会掩盖结构差异。
- **单模型。** 结构与模型的交互未知。v1 不比较模型。换模型要整批重跑，不能只换一臂。
- **提示词仍是混杂因素。** 三臂共用提示词，但提示词会偏向某一种写法（例如鼓励短标题）。提示词版本要入库，改词视为新实验。
- **并发与锁没有在 v0.1 测量。** 不能用 `fcntl.flock` 的存在推断多代理正确性。
- **sapper-v2 与 Cairn 的比赛结果在范围外。** 它们改变了编排、角色、模型和知识库内容，且数字是自述，来源之间的 token 数也不一致。
- **范围外的任务形式：** 生成或优化利用代码、对真实目标发送攻击流量、提交 flag、比较渗透教令、把 GraphRAG 索引费用算进 v0.1 的单次查询。

## 8. v0.1 里程碑

最小的、已经能提供信息的实验是：

1. 冻结配置：模型、`B_inject`、`N_steps`、`limit`、随机种子、16 个 Juliet 题的抽样规则。
2. 实现三个适配器，使第 3 节的四个工具在空库上行为符合该节表格。为每个工具写一条不调用模型的契约测试。
3. 实现脱敏器，并完成 10 个文件的人工抽查记录。
4. 跑 144 次写入 + 144 次交接。用第 5 节的程序出表：每臂的判断准确率、类别准确率、位置命中、证据忠实度、输入/输出 token 的中位数、失败率。
5. 在 `docs/status.md` 记录配置哈希和轨迹目录。不在轨迹还没抽查之前写“某结构更好”。

v0.1 不包含并发压测、PrimeVul、OWASP Benchmark 的运行、Joern、MemGPT 第四臂。
